# F06 Azure provider contract

Feature-local interface; consumes merged F01R DTOs without schema changes. Public import location: `cloud_network_benchmark.azure_provider`. F09 integrates these functions later. No cloud call occurs merely by importing or building a request.

## Functions

| Interface | Input | Output |
| --- | --- | --- |
| `build_pair_inputs(deployment, options)` | Azure `ProviderDeploymentInput`, private `AzureRuntimeOptions` | Validated Terraform variables and deterministic recovery intent; pure, no runner |
| `register_expiry(deployment, request, options, runner, *, clock, utc_now)` | Same request with reserved evidence; `ExpiryRequest(action=deallocate)` and fixed original deadline mapping | Existing `ExpiryEvidence`; local journal retains all commands/failures even on failed registration |
| `provision(deployment, options, runner, *, clock, utc_now)` | Azure deployment with matching confirmed `reservation` and `expiry`; same private workspace and deadline | `AzureProviderResult` with full or explained partial normalized output and cleanup-required |
| `destroy(deployment, options, runner, *, clock, utc_now)` | Same identity/options and private recovery journal, even when provision returned partial output | `AzureCleanupResult`, residual blocking and expiry cancellation evidence |

`clock` and `utc_now` are injected monotonic and aware UTC callables. Derive the original monotonic end once at reservation handoff and persist that mapping; never derive a fresh duration after a command. The options/journal must carry the original mapping on recovery. Each command is a `CommandRequest` with argv, cwd, finite clipped timeout and redactions, never a shell string. Routine invalid input fails before mutation; external failures return typed evidence and preserve the private journal. The caller invokes destroy on failed registration/preparation when resources may exist. F09 calls destroy after native results close/copy/verify, or on failure with primary evidence preserved; F06 never retrieves measurements.

## Admission and expiry preconditions

Require provider Azure and matching run/deployment/campaign/config/namespace; reserved state and reservation ID; nonzero remaining time; cap start before current action; dated cost identity including expiry; caller admission snapshot with no outstanding cleanup and explicit priority review when required. Do not implement F11 ledger or infer P2/P3 admission from scenario support. The caller must supply an admitted deployment; local evidence must retain that origin. `complete_workflow_seconds` is a conservative total from `cap_started_at`; after registration and before pair apply use the independent conservative `post_registration_workflow_seconds` bound from current time. Never subtract a registration overrun from required measurement/copy/cleanup time. Required mode duration plus caller-supplied remaining setup/copy/cleanup bounds must fit. No invented mode allowances.

`register_expiry` requires actual trigger earlier than retry-end and retry-end no later than reserved cap. Both at initial check and after readback, projected complete-workflow end must fit before actual trigger. Before schedule mutation require at least 300 seconds until the trigger; after binding readback require enough remaining complete-workflow time and no passed trigger. `provision` independently rejects not_registered/failed/cancelled/triggered/stale/mismatched expiry, malformed metadata or mutated publication/binding/target evidence. It reads back the registered action again before pair apply; an expiry DTO with a plausible ID is not sufficient. Preserve `cap_started_at <= expiry.registered_at <= pair_apply.started_at`.

## Terraform roots

- `terraform/azure/expiry`: only attempt resource group, Basic Automation account with system identity, narrow custom Compute read/instanceView/deallocate role and assignment at that group. No VM or pair network. Exact future A/B IDs derive from subscription/group/role names, not VM outputs. Account/role readback and module readiness must succeed before registration.
- `terraform/azure/pair`: uses existing attempt group name/ID, never owns/deletes the expiry group. Exactly two Linux VMs plus two boot disks (VM-managed), two accelerated NICs, two Standard static public IPv4s, per-VM NSGs, run VNet/subnet(s), Standard PPG only S3, two explicit peerings only S4. No native VM expiry fiction, NAT, load balancer, bastion, agents or external state. Both roots have local state under the private attempt root, separate `TF_DATA_DIR`, bounded operations and run/config/deployment tags. No `-target` dependency trick and no shared default Terraform state.
- Preserve image selection/version and Regular purchase semantics. Source options `eviction_policy/max_price` are not sent as Spot arguments on a Regular VM. Output exact resource IDs/addresses/image/zone/shape/PPG/acceleration and inventory. `documented_network_limit` records 12,500 Mbps maximum aggregate and the Dsv5 source; actual measurements never fabricated.
- Private addresses are deterministic within declared subnets: e.g. A `.4`, B `.5` in Frankfurt for S1–S3, London B `.4` for S4. Require no reserved-network address and no overlap within the run. Same CIDRs in isolated concurrent attempts are permitted, with no cross-attempt peering. NSGs explicitly allow controller /32 SSH then deny other SSH; on B allow A /32 UDP11111/TCP5201/ICMP then deny other sources before broad Azure default virtual-network allow rules. Guest MTU/CUBIC/ECN settings are applied in the minimal cloud-init input, verified by existing downstream preparation/diagnostics rather than asserted as observed provider values.

## Automation operations

All API fields below are genuine Azure Automation `2024-10-23` contracts linked in research.md, not VM properties. Under the observed account ARM ID:

1. PUT `runbooks/<name>` with location, `properties.runbookType=PowerShell`, draft properties and no external content URL. PUT `runbooks/<name>/draft/content` with exact local script bytes and appropriate content type. POST `runbooks/<name>/publish`; follow bounded completion/readback and GET published content to verify digest and state. No execution is requested merely to register.
2. PUT `schedules/<name>` with `name`, `properties.frequency=OneTime`, explicit `properties.startTime` UTC and `properties.timeZone=UTC`. Read back `isEnabled`, exact returned UTC start and no unexpected recurrence. Preserve minute rounding; reject changed timing that violates fit/cap.
3. PUT `jobSchedules/<uuid>` with `properties.runbook.name`, `properties.schedule.name`, lower-case parameter keys for exact target IDs, subscription, deployment binding, retry-end and polling ceiling. `runOn` omitted/empty for Azure cloud execution; no Hybrid Worker. GET and compare complete binding. The observed ARM jobSchedule ID is registration_id.
4. Read back principal, role scope/actions/assignment, runtime/module state and script digest; persist registration only after all match. Any missing/denied/draft/stale/partial response produces failed/not-registered evidence and zero VM creation. Never treat an unverified JSON fixture as actual Azure success.

Runbook uses system managed identity and only Azure REST GET/read-instanceView and POST `/virtualMachines/<name>/deallocate?api-version=2025-04-01`, without hibernation. It validates the exact pair namespace/subscription, handles A and B independently, observes long-running status and per-target PowerState/deallocated, rechecks absent/creating targets until the finite retry-end, clips HTTP/poll waits and records structured outcomes. No start/recreate or delete action. An expired/late job records that condition; it may make an immediate best-effort deallocate request for each exact target with a finite request timeout, without claiming it met the original cap. No unbounded recovery loop. Late job minutes must be included in the conservative expiry cost bound.

Azure retains account/runbook/schedule/job/identity independently of controller memory; local recovery retains names/IDs even if registration fails between steps. Declared RBAC readback cannot prove effective authorization or dispatch SLA. Paid controller-loss acceptance must prove actual schedule registration, runtime, both deallocations and subsequent complete deletion.

## Authenticated host identity and normalized output

After pair creation, invoke authenticated Azure action Run Command against each exact VM ID with a fixed read-only script returning `/etc/ssh/ssh_host_ed25519_key.pub` (or an explicitly supported public host-key type). Require matching subscription/resource identity, successful completed execution, valid public-key format and bounded output, then materialize a private per-attempt known_hosts bound to the observed public IP/port. Keep public key fingerprint/source-action identity in redacted evidence; never retrieve private host keys or trust SSH keyscan. Use public address for `RemoteConnectionData.host` and private address for benchmark metadata. Preserve connection_user and strict F02R references. No SSH/benchmark call is needed for F06 offline checks; fakes return provider-authenticated public-key evidence and create actual local known_hosts bytes.

Terraform output normalization never invents missing image IDs, physical zones, host keys or acceleration. For partial output use per-role unavailable evidence; no usable connection until host identity is authenticated. `ProviderDeploymentOutput.started_at` is pair apply start, after registration, and output expiry matches this attempt. Keep actual UTC/action evidence and explain clock anomalies instead of synthesizing time.

## Cleanup and recovery

Write intent before any expiry/pair mutation; keep separate state and exact expected/discovered ARM IDs. Invoke pair destroy after creation may have started even if apply/output failed. Bound every command by original deadline and preserve failure history. Inspect VMs/disks/NICs/IPs/networks/peerings/PPG by expected IDs plus scoped full group inventory; Azure API failure/202/unknown inventory is not absence. Reject foreign resource ownership rather than deleting it.

Until both VMs are verified absent, retain the expiry schedule, runbook, account, identity and roles. Then remove remaining owned pair resources, unlink/delete job schedule and schedule, remove runbook, destroy expiry prerequisites/group and re-inventory. Cancellation and cleanup failure are separate evidence. No automatic data retention, extension, campaign retry or broad subscription sweeper. Return failed/open with `launch_blocked=true` for residual or unknown inventory; F09/F11 consume that result to block new launches.
