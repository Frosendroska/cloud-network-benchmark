## Decision 1: Azure Automation once-only deallocation

**Decision**: A single attempt resource group contains a Basic Automation account with system-assigned identity, a published deallocate-only PowerShell runbook, one date-specific UTC schedule and one job binding. The same group holds the two deterministic future VM IDs and pair resources, including London resources when needed. The controller reserves first, prepares expiry resources, publishes and reads back the executable action, registers/reads back the schedule/binding/permissions, then permits the separate pair apply. Azure stores execution content, identity, parameters and schedule; no controller connection is needed at trigger time.

**Rationale**: [Automation schedules](https://learn.microsoft.com/en-us/azure/automation/shared-resources/schedules) support one-time execution and parameters. The [schedule REST contract](https://learn.microsoft.com/en-us/rest/api/automation/schedule/create-or-update?view=rest-automation-2024-10-23) takes an absolute start time; the [job schedule contract](https://learn.microsoft.com/en-us/rest/api/automation/job-schedule/create?view=rest-automation-2024-10-23) binds runbook/schedule names and parameter strings, with no VM existence dependency. Registering deterministic future IDs in those parameters before VM creation is our engineering inference from these contracts; real behavior remains a paid-acceptance check. Do not claim the documentation proves a deployed pre-create test.

**Alternatives**: Guest shutdown leaves Azure compute allocated. [VM auto-shutdown](https://github.com/MicrosoftDocs/azure-compute-docs/blob/main/articles/virtual-machines/auto-shutdown-vm.md) is an existing-VM daily-time workflow; no supported pre-create/date-specific guarantee was established. Start/Stop VMs platforms, Functions, Logic Apps, workers and local timers add infrastructure or fail controller independence. The selected narrow runbook is the required expiry mechanism, not a general service.

## Decision 2: Genuine publication and state evidence

**Decision**: Terraform creates the expiry account/group/custom role/assignment in an isolated expiry state. The local Azure driver uses authenticated `az rest` through `CommandRunner` for [runbook draft creation](https://learn.microsoft.com/en-us/rest/api/automation/runbook/create-or-update?view=rest-automation-2024-10-23), [content upload](https://learn.microsoft.com/en-us/rest/api/automation/runbook-draft/replace-content?view=rest-automation-2024-10-23), [publish](https://learn.microsoft.com/en-us/rest/api/automation/runbook/publish?view=rest-automation-2024-10-23), schedule and job binding, all Automation API `2024-10-23`. Read back Published state and published content SHA-256, exact schedule UTC/enablement, job target parameters and role assignment before returning registered. Poll asynchronous publication within the original deadline.

**Rationale**: Explicit draft/upload/publish avoids a remote content-hosting requirement or fabricated native expiry fields. The [Terraform runbook documentation](https://raw.githubusercontent.com/hashicorp/terraform-provider-azurerm/main/website/docs/r/automation_runbook.html.markdown) notes content-link constraints; no fake URL or object store is introduced. Terraform still owns pair infrastructure and expiry identity prerequisites. REST-created expiry children are included in the same recovery inventory and removed before account destruction. No speculative generic API adapter is needed.

**Runtime**: Use the supported classic `PowerShell` runbook runtime (5.1) and Az.Accounts module for `Connect-AzAccount -Identity` and `Invoke-AzRestMethod`; no AzureRM PowerShell. [Modules](https://learn.microsoft.com/en-us/azure/automation/shared-resources/modules) and [runbook types](https://learn.microsoft.com/en-us/azure/automation/automation-runbook-types) distinguish module/runtime versions. Read back required module provisioning success/version; missing or incompatible modules block creation. Record runtime/module identity and script digest. No automatic upgrade platform is introduced. Actual execution compatibility remains a paid acceptance requirement.

## Decision 3: Deallocation, retries and permissions

**Decision**: Runbook parameters contain exactly two validated VM ARM IDs, the subscription, attempt/deployment binding and absolute retry-end UTC. The identity receives only `Microsoft.Compute/virtualMachines/read`, `Microsoft.Compute/virtualMachines/instanceView/read` and `Microsoft.Compute/virtualMachines/deallocate/action`, scoped to the attempt group. No VM start, create, delete, broad Contributor or subscription VM discovery permission. Controller permissions are distinct: create/read/delete the pair/expiry resources, custom role definition/assignment management, runbook draft/content/publish/schedule/job access, inventory and authenticated Run Command. Account-provider registration and role-management entitlement are separate paid preflight checks; offline code never registers a cloud provider.

**Rationale**: Azure's [deallocate REST operation](https://learn.microsoft.com/en-us/rest/api/compute/virtual-machines/deallocate?view=rest-compute-2025-04-01) releases compute and can return 202. Use that endpoint without hibernation; request acceptance is not completion. The narrow actions are documented in [Compute roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/compute). An identity/role readback proves declared configuration, not effective permission propagation. Revocation, policy denial and service outages remain possible.

**Failure behavior**: Attempt both IDs even if one fails. Re-observe and retry absent/creating/transient targets using finite configured polling and the supplied absolute retry end (at or before the reservation end); never terminate early merely because both IDs initially return 404. Record 404 as absent at that instant, not proof that an in-flight create cannot later complete. Deallocated status requires instance-view observation. Late completion after the bounded action, denied requests and delayed dispatch remain explicit unresolved safety/cleanup evidence. No bounded local design guarantees ARM completion or hard billing cutoff. The fake clock must cover a target that appears after the first scheduled check.

## Decision 4: Lifetime and costs

**Decision**: `cap_started_at` is reservation activation before expiry preparation. Preserve `cap_started_at <= registered_at <= pair_apply.started_at`; expiry request trigger is no later than reservation expiry. Use a caller-supplied complete-workflow bound, including expiry setup, apply/bootstrap/readiness/stabilization, mode duration, post-measurement copy and cleanup, and reject if its projected end exceeds the actual trigger. Recheck elapsed remaining time before every mutation; do not reset deadlines. Any earlier trigger and finite retry allowance are explicit caller inputs, not new study defaults or cap extensions.

**Lead**: [AzureRM schedule documentation](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/automation_schedule.html) requires start at least five minutes ahead. Adopt a conservative minimum 300-second remaining lead at registration and recheck the returned time/binding before pair apply; reject a schedule rounded earlier than the planned workflow or altered beyond the cap. No rounding forward beyond the cap. Short/acceptance, calibration and day caps remain 1,200/1,800/87,600 seconds. Registration delays can make the 24-hour mode inadmissible; reject rather than enlarge its cap. An explicit earlier trigger may also make a workflow infeasible.

**Costs**: [Automation pricing](https://azure.microsoft.com/en-us/pricing/details/automation/) charges job minutes, with account/subscription free-unit conditions. Do not assume free units remain or hardcode a live rate. Require identified dated price inputs for compute, disks, public IPs, transfer/peering, and worst-case bounded expiry job minutes. Registration/setup consume reserved lifetime even before VM billing starts. Missing expiry pricing blocks provisioning. Existing $147.82 forecast is based on 14 October inputs and does not prove this mechanism has already been included. F11 reserves within $300/$50 protected. F06 reports mechanism usage inputs; no ledger or price service. Deallocation leaves disks/public IPs and other resources; normal full deletion and inventory remain mandatory.

## Decision 5: Azure-specific pair and identity

**Decision**: Two explicit `azurerm_linux_virtual_machine` roles, `priority=Regular`, no Spot-only eviction/max-bid fields even though legacy-compatible V2 provider options retain `eviction_policy`/`max_price`; preserve those input values in source evidence, never send them as active Spot configuration. Use StandardSSD_LRS with `disk_size_gb=32` (the selected E4 tier), Standard static public IPs with matching logical zones, one accelerated NIC and fixed private addresses derived from the declared /24. Standard PPG uses the ordinary resource, shared by both zone-1 VMs; include `allowed_vm_sizes=[Standard_D4s_v5]` with zone intent if a zone is specified. No Ultra PPG or host-affinity guarantee. S4 has two VNet peerings, no gateways or NAT.

**Rationale**: [Dsv5](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/general-purpose/dsv5-series) documents 4 vCPU, 16 GiB, no local disk and maximum aggregate 12,500 Mbps for D4s_v5, not a throughput guarantee. [PPG](https://learn.microsoft.com/en-us/azure/virtual-machines/co-location) describes colocation and capacity limitations; [Terraform PPG](https://raw.githubusercontent.com/hashicorp/terraform-provider-azurerm/main/website/docs/r/proximity_placement_group.html.markdown) requires allowed sizes when zone intent is set. [Global VNet Peering](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview) supplies private regional routing. Azure logical zones remain subscription-local; no physical zone mapping is invented.

**Host authentication**: Use Azure-authenticated action Run Command during bootstrap to read the VM's public SSH host key, bind response to its exact VM resource ID and observed public address, then materialize attempt-private known_hosts without overwrite. [Microsoft's SSH guidance](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/mac-create-ssh-keys) explicitly recommends Run Command fingerprint validation. [Linux Run Command](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command) requires guest-agent/outbound connectivity, bounds output and has significant invocation latency; the tiny public-key response fits, and its latency consumes setup budget. No SSH keyscan trust, shared known_hosts or private host keys. Keep platform-agent/package egress needed for bootstrap; no benchmark listener is public and no management identity invocation occurs during measurement.

## Decision 6: Recovery and scope

**Decision**: Keep a private attempt workspace with isolated pair/expiry state and a write-before-action recovery journal of deterministic names/IDs. Failed apply still triggers scoped inventory/destroy even without output. Exact resource IDs plus attempt binding, not tags alone, define deletion scope. Verify removal through direct resource GETs and group inventory; unknown responses fail closed. Deletion order retains independent expiry until both VMs are verified absent, then removes pair residuals, schedule/binding/runbook/role/account/group. If pair or VM absence is unknown, do not remove expiry or its identity/RBAC. Journal survives interrupted cleanup; no automatic new experiment, resource adoption or result-disk retention policy.

**Boundary**: F09 performs measurement closure/retrieval before invoking normal deletion; F06 exposes cleanup and does not copy native results, choose N, schedule research, alter F02R/F03/F04/F08/F11, or claim real cloud acceptance. Azure-local result/cleanup records use existing Evidence/FailureEvidence/CleanupState types; no shared schema amendment is required. Focused fakes exercise external argv and materialized state/journal/evidence, while Terraform mocked plans exercise actual HCL expressions.
