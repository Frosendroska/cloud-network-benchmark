## D1 — Use current public component boundaries

**Decision**: Compose existing contracts/functions; add no shared DTO/schema.
**Rationale/evidence**: `manifests.py:725 initialize_campaign`, `lifecycle.py:35/49/56` transitions/aggregation; `admission.py:661 reserve`, `:924 check_stage_fit`, `:984 claim_creation`, `:1074 reconcile`; `providers/aws.py:151 AwsProviderDriver` register/provision/cleanup; `providers/gcp.py:138 GcpProviderDriver`; `azure_provider.py:777/916/1057` register_expiry/provision/destroy return their provider-specific results. `access.py:265/270/275` prepare/check_readiness/retrieve accept ConnectionOutput/RemoteDeadline and replaceable CommandRunner. Adapters normalize only orchestration handoffs, preserving complete native result/recovery evidence and explicit provider settings. Registration failure and uncertain creation can create cleanup liabilities even without pair output.
**Alternative rejected**: Generic backend platform or edits to already merged provider semantics; neither is needed for three explicit branches.

## D2 — Run F03 on A, not over a fake controller-local process adapter

**Decision**: Add a narrow `lifecycle_guest.py` entry, stage the exact controller package source archive/wheel and record its SHA/revision on prepared A. Bootstrap a per-deployment Python environment with existing project dependencies, record Python/dependency versions and verify import/package digest before invoking F03. Stage preparation uses existing SSH/SCP identity/deadline/redaction rules and is part of readiness allowance; failures prevent measurement. Do not prescribe an external software freeze or silently execute a different installed package. Offline tests fake installer/transport commands and invoke the guest entry with fake native processes, so they require no download/cloud/traffic.
**Rationale/evidence**: F03 `specs/005-v2-measurement-runner/spec.md:88` explicitly promises an A-local callable without SSH; `measurement.py:898 run_measurement`, `measurement_process.py:70 LocalMeasurementProcesses` use local files/subprocesses. A controller-local call would send traffic from the wrong machine; an SSH-per-client shim would misstate clocks and require premature native copies. `diagnostics.py:41 build_collection_context` + `diagnostics_guest.py:570 main` already provide the standalone B/A diagnostic entry.
**Alternative rejected**: New agent/service, duplicated standalone measurement engine, controller-side traffic, or periodic remote synchronization. The guest entry is one bounded command plus scoped cancellation/control, not a daemon.

**Offline runtime staging assumption**: The adapter copies only the package source and selected revision marker over the existing trusted SCP transport, verifies the archive SHA-256 and marker on VM A, creates the destination before SCP, and creates a per-deployment venv. Ubuntu Noble's `python3-pydantic` package is 1.10.14, while this repository requires Pydantic 2; therefore the venv installs the existing declared project ranges (`pydantic>=2,<3`, `PyYAML>=6,<7`) during bounded guest preparation and records actual installed versions before F03 invocation. Offline checks fake this installation command; no cloud or guest install is run here. The source digest excludes generated bytecode, so importing the exact staged package does not change its identity. No separate software-freeze gate is implied.

## D3 — Reuse F11 cap activation, claims and final-copy retry

**Decision**: Reserve immediately before protection, use full remaining WorkflowAllowance/check_stage_fit at boundaries, call claim_creation only with all selected providers' exact request/evidence sets. Use one controller session explicitly across healthy independent invocations. At most one retry per failed artifact through bounded_copy_handoff; its work deadline is min(original cap, provider trigger) minus positive cleanup allowance.
**Rationale/evidence**: `admission.py:285 WorkflowAllowance`, `:334 AdmissionPlan`, `:394 bounded_copy_handoff`; `specs/011-v2-schedule-budget/contracts/schedule-admission.md:36–40`; F11 spec resolves start/copy in Clarifications. These are already ordinary adopted engineering choices. No 15-minute copy checkpoint or new cap is introduced.
**Alternative rejected**: Reset cap after readiness/restart, stage-only fit, retry all files/campaigns, automatically recover retained disks.

**Retrieval boundary clarification (T014)**: Existing `retrieval.run_retrieval` historically made up to two transfer attempts per item in a single call. Its keyword-only `max_attempts` accepts only strict integers `1` or `2` and defaults to `2`, preserving F02 behavior. F09 calls it with `max_attempts=1`, obtains only failed concrete IDs, evaluates `bounded_copy_handoff` against the same original `RemoteDeadline` and sourced copy/cleanup allowances, then calls a filtered one-item manifest with `max_attempts=1, attempt_offset=1` only after a fresh F11 admission callback. The explicit offset preserves unique command IDs and campaign-wide attempt numbering across calls; total attempt numbers cannot exceed two. F09 skips retry after an interrupted source inventory/transfer. Campaign evidence preserves first-round failures and partial bytes; successful destinations are never selected. This is a narrow backward-compatible integration boundary, not a new retry policy or shared DTO.

## D4 — Partial-provider execution and durable recovery

**Decision**: A failed registration blocks every create. After complete protection, provision/readiness failure is provider-local; healthy peers continue only within full remainders. Mark missed rows without measurement. Persist identities/private references before side effects; collect all peer outcomes. Do not resume measurements or uncertain creation after restart; explicit cleanup uses journals and reconciles only proved absence/charges. Unknown/remaining resources stay blocked in F11. Independent compute stop/deallocation is never a cleanup success.
**Rationale**: Thesis runtime explicitly records partial-provider failures, normal deletion, controller loss and residual blocking; provider journals already retain uncertain creation and safety resources. Reachable failures attempt finalization; abrupt-loss fakes intentionally skip finalizers.
**Alternative rejected**: Fail-fast futures that abandon peers, claiming cleanup on planned expiry, automatic measurement retry/recovery platform.

## D5 — Declare actual bytes and bind only after final retrieval

**Decision**: Start with ArtifactLayout's mode declarations; append explicit supplemental ArtifactInput entries for four bootstrap build-identity files and distinct per-unit Sockperf stdout/counter logs. Use actual build IDs (currently `f02r-{role}-{tool}-build`), exact produced paths, kind/producer/unit. Preserve deployment-scoped receiver logs/builds with unit_id=None. For DAY use family declarations and concrete chunk IDs/paths exactly as the merged018 contract requires. Do not copy F08 model_copy fixtures as canonical construction.
**Rationale/evidence**: `contracts/artifacts.py:35 ArtifactInput`; `contracts/validation.py:41 ValidatorInput` canonical_roles accepts explicit matching supplemental declarations; `bootstrap.py:166 materialize_build_identity_artifacts`; `measurement.py:491` delegates aggregate stdout/stderr projection to F09; `specs/016-native-acquisition-evidence/contracts` requires actual closed/retrieved B sources; `specs/018-day-artifact-identity` fixes family/concrete identities. `acquisition.py:736 bind_acquisition_sources` reconstructs proof from actual observations/builds/verified source records after retrieval, and `:543 iter_source_windows` checks it. No BuildObservation field is added to ValidatorInput; sidecar bytes and existing metadata are sufficient. Never infer identity/proof from a label/version.

Build identity records may already be materialized on the controller by bootstrap.materialize_build_identity_artifacts from the original captured SSH sidecar bytes; retain observed role origin but do not pretend those paths physically exist on B. Separate these exact controller-captured source records from the remote retrieval subset. If F03 materializes identical copies on A, deduplicate by exact ID/path/bytes rather than inventing a second source or copying a B-origin path from the wrong VM. The final remote inventory still retrieves all actual measurement/diagnostic/receiver files from their real producers.

**Alternative rejected**: Relaxing canonical validation/unique IDs, repeated `sockperf-log`, unverified hashes, model_construct/model_copy shortcuts or invented closure/acquisition fields.

## D6 — Separate terminal state, validation and sealing without cycles

**Decision**: Update existing manifest fields through validated atomic helper(s); terminal execution records the actual command workflow (validation data verdict separate), cleanup records verified deletion. Persist complete terminal snapshots/input before F08; F08 `validation.py:386–460` checks strict manifest projections and DAY excludes child probe chunks by design. All chunks stay in ValidatorInput. Persist the resulting validation status without altering captured execution/source evidence, recompute campaign aggregation and peer comparison eligibility. Seal only after no further result mutations; checksum index excludes itself, while its hash may be returned to the user outside that index. Validation input/result are controller artifacts outside native source-record inventories to avoid cyclic input/self hashes.
**Rationale**: Existing ChildRunManifest already has reservation/expiry/commands/timings/artifact_records/retrieval_failure/validation_status; only update helpers are missing. `validate_bundle` is pure and F09 owns persistence. Execution success cannot imply valid data or cleanup, and campaign summary must distinguish them explicitly.
**Alternative rejected**: Marking clean exit as valid data, changing raw bytes after validation, self-hash cycles or widening shared models.

## D7 — Serialize CLI integration and keep paid evidence honest

**Decision**: F09 owns isolated lifecycle_cli plus final narrow cli dispatch only after coordinator release/latest-main F12 integration. Keep F12 analysis commands/modules untouched. Offline preview/fakes are usable now; real execution paths remain blocked by existing missing paid-acceptance/support/dates/refresh prerequisites until separately authorized evidence exists. User-facing docs describe actual command selection and outcomes, not internal workflow artifacts.
**Alternative rejected**: Concurrent replacement of cli.py, a second executable platform, weakening paid gates for a demo. No new research decision or human approval is needed for these engineering choices.
