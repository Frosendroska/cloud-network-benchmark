## 1. Pre-create native registration

**Decision**: Create and read back two immutable global instance templates before pair creation. Each has absolute `properties.scheduling.terminationTime`, `instanceTerminationAction=STOP`, `provisioningModel=STANDARD`, no relative maxRunDuration and automatic restart disabled. Bind each standalone VM to its exact registered unique template ID; no scheduling or other content overrides.

**Rationale/source proof**: The [Compute Engine instanceTemplates.insert API](https://docs.cloud.google.com/compute/docs/reference/rest/v1/instanceTemplates/insert) accepts these scheduling properties. The [instance-template CLI reference](https://docs.cloud.google.com/sdk/gcloud/reference/compute/instance-templates/create) explicitly applies automatic time-limit actions to templates. [Create a VM from an instance template](https://docs.cloud.google.com/compute/docs/instances/create-vm-from-instance-template) states default inheritance, with name/zone exceptions, and documents `instances.insert?sourceInstanceTemplate=...` and optional override semantics. Together these support registering the provider-native definition first, then inheriting it atomically during creation. Provider execution of the VM time-limit policy is independent of the controller; a bare local Terraform variable or an instance-only scheduling field does not establish prior registration.

**Binding evidence**: Get each template by authenticated project identity; retain numeric ID, creation time, exact properties, expected role/locality and canonical hash in the private journal. Require template readback before declaring registration; repeat immediately before pair apply. Use [HashiCorp's documented self_link_unique](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/compute_instance_template.html.markdown) with uniqueId, and [compute_instance_from_template](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/compute_instance_from_template.html.markdown). The pair root has only name/project/zone/source-template/timeouts; static tests reject overrides. Post-create `instances.get` must match scheduling. Do not assume instances.get returns a source-template field: exported binding proof is the actual request/config plus independent observed properties.

**Alternatives considered**: Instance-only maxRunDuration starts too late, can reset on restart and is not a pre-created registration. Instance-only terminationTime also lacks a separately observed pre-create resource. Compute instance schedules are regional, have larger scheduling delay and compete with S3's one supported resource-policy slot; avoid them for this feature. Cloud Scheduler direct stop would add a service when native templates suffice; Cloud Tasks/PubSub/Functions/MIGs/agents are unnecessary and excluded.

## 2. Original cap and earlier trigger

**Decision**: Original cap start is observed reservation activation. Require source-identified reserved complete-workflow costs, no cleanup blocker, and `cap_start <= registered_at <= pair_apply_start`. The actual absolute trigger T is reserved cap end minus 30 seconds. `ExpiryRequest.expires_at` and `ExpiryEvidence.expires_at` both identify T, while provider_metadata retains the cap endpoint and policy ID. Never extend either after creation, restart or retry.

**Rationale**: [Limit VM runtime](https://docs.cloud.google.com/compute/docs/instances/limit-vm-runtime) documents native STOP, a timestamp at least 30 seconds ahead and up to 30 seconds of delay before termination begins. A timestamp remains fixed across reruns, whereas duration restarts. The 30-second lead is a conservative engineering request, not an operation-completion or billing bound. Check a supplied positive whole-workflow remaining estimate fits before T at registration and immediately before apply; it must include remaining setup/preparation/stabilization, the complete selected mode, final copy and cleanup. Delayed registration that makes this impossible fails closed. Do not invent stage allowances, fixed copying timers, increased day caps or successful paid timing. UTC anomalies that invalidate the source cap/time ordering fail closed; command elapsed timing remains monotonic where available.

## 3. Governing STOP versus current executable DELETE

**Finding**: On base e03a07e, `contracts/campaign.py:301` and `contracts/deployment.py:189` require GCP `instance_termination_action=DELETE`; all GCP executable configs carry DELETE. The [template CLI termination-action definition](https://docs.cloud.google.com/sdk/gcloud/reference/compute/instance-templates/create) applies the field to automatic time limits as well as preemption. It cannot be passed through as DELETE for this stop-only fallback or silently overridden.

**Disposition**: Coordinator authorized serialized `F01R_GCP_EXPIRY` (`specs/017-gcp-stop-contract/`) migration under existing stop governance. It owns both validators, config GCP blocks, generated shared schemas and affected fixtures/tests/dry-run descriptions. F07 owns none of them. Implementation is gated until a verified merge accepts STOP, rejects DELETE, regenerates deterministic schemas and passes affected checks. This is a known internal integration blocker, not an unresolved research choice. The F07 design specifies the governing STOP interface, not falsely current runtime support.

## 4. Exact topology and settings

**Decision**: One attempt custom VPC with MTU 1460, subnet `10.80.1.0/24` in europe-west3 and `10.81.1.0/24` in europe-west2 only for S4. Reserve A `.10` and B `.11` in Frankfurt for S1–S3; S4 A `10.80.1.10`, B `10.81.1.11`. These usable host offsets are engineering choices within the selected CIDRs. Global templates have role-specific subnet/IP and one ephemeral public management address. Duplicate primary CIDRs across independent runs are safe only because VPCs/state/IDs are separate; do not peer them.

**Rationale/sources**: [VPC networks](https://docs.cloud.google.com/vpc/docs/vpc) are global, with regional subnets and automatically generated subnet routes. One custom network therefore supports S4 private addressing without inter-region peering. S1 is a/a, S2 a/b, S3 a/a compact, S4 Frankfurt-a/London-a. [Compact placement instructions](https://docs.cloud.google.com/compute/docs/instances/use-compact-placement-policies) support N2 COLLOCATED without maxDistance, and [placement overview](https://docs.cloud.google.com/compute/docs/instances/placement-policies-overview) limits interpretation to best-effort compactness and states no extra placement charge. Only S3 consumes one resource policy, so native time-limit scheduling does not compete with it. Use MIGRATE host maintenance supported by this no-distance N2 policy; record actual policy, not a claim of physical adjacency.

**Machine/image**: Retain n2-standard-4, 4 vCPU/16 GB, pd-balanced 32 GiB, gVNIC with no Tier_1. [General-purpose machine documentation](https://docs.cloud.google.com/compute/docs/general-purpose-machines) supplies documented N2 egress up to 10 Gbit/s for this shape, not measured throughput. [Canonical's GCE image guide](https://ubuntu.com/gcp/docs/google-how-to/gce/find-ubuntu-images/) identifies ubuntu-os-cloud/ubuntu-2404-lts-amd64. Require an exact immutable supplied image and authenticated describe including amd64/GVNIC compatibility; current family is a selector, never exact output evidence. Default N2 CPU platform is not a guaranteed observed CPU model; do not force Ice Lake or substitute zones.

## 5. Security, trust and permissions

**Decision**: Exact controller /32 ingress TCP22 to both role tags. B ingress UDP11111/TCP5201 only from A /32; pair-only ICMP, no broad all-private ingress. Use exact ranges without source_tags OR rules that could widen access. Default deny ingress. Attempt public key in template metadata; block project SSH keys, disable OS Login for this explicit key/guest-attribute path, enable guest attributes; no password/accept-new/unchecked keyscan. No VM service-account credentials/scopes are required for benchmarking.

**Host trust**: Google's [secure connection guidance](https://docs.cloud.google.com/solutions/connecting-securely) and [guest-attribute guide](https://cloud.google.com/compute/docs/metadata/manage-guest-attributes) document guest-agent publication of host keys and authenticated API retrieval. Fetch `hostkeys/` using `instances.getGuestAttributes`; its [API response](https://docs.cloud.google.com/compute/docs/reference/rest/v1/instances/getGuestAttributes) contains queryValue.items, not an invented boot proof. Check authenticated instances.get project/zone/numeric ID before and after query, bind known_hosts to observed public IPv4, reject changed identity or invalid/missing keys. Guest attributes are guest-supplied evidence under tenant/guest-agent trust, not hardware attestation; preserve this limitation. F02R owns actual SSH comparison and readiness; no real SSH occurs here.

**Permissions boundary**: Caller preconfigures project APIs and authenticated CLI/Terraform identity outside exported data. Required capabilities include instanceTemplates create/get/delete/useReadOnly, instances create/get/list/delete/getGuestAttributes, network/subnet/firewall create/get/list/delete/use, compact resourcePolicies create/get/list/delete/use and image get. Normal cleanup and verification require their actual scoped permissions; registration/readback cannot prove future permission success. No service activation, project IAM edits, account-wide role grants or guest service account are created by F07. Document minimal capability checks and denied-operation failures; paid acceptance validates real IAM.

**Bootstrap boundary**: Preparation content comes from the existing handoff. Template settings describe MTU/CUBIC/ECN/DSCP/offloads and expected image/NIC; F02R/F04 later verify actual guest state. Bootstrap package/metadata access must not become a measurement requirement or a new monitoring service.

## 6. Cost and cleanup

**Decision**: Check a dated provider-local cost fixture in `tests/fixtures/gcp/cost-inputs/` at implementation: source URLs, checked date, mechanism version, hash, unit and explicit zero support charge rationale. [Instance-template pricing](https://docs.cloud.google.com/compute/docs/instance-templates) states templates have no added charge; native scheduling adds no separate resource/service. Placement is likewise no-additional-charge per the placement source. This does not make VMs, boot disks, public IPs, transfer, tax or uncertainty free; caller reservation must include them using identified dated run-register inputs, not new hardcoded live prices. [Disk/image pricing](https://cloud.google.com/compute/disks-image-pricing) defines GiB as 2^30 bytes. Throughput remains decimal Gbit/s. No current paid-price quote is claimed.

**Cleanup order**: Preserve original private states and IDs after uncertain operations. Destroy pair and verify compute absent before deleting protection root/network. Template deletion alone does not undo scheduling inherited by a VM. Only verified all-resource absence can close cleanup and mark registration cancelled. Native STOP leaves persistent disk/IP/resource accounting open. Inventory both S4 regions plus global resources, known VM/disk/network/policy IDs and all pagination; unknown/denied inventory is failure. Do not treat not-found for another project/identity as verified absence. No automatic recovery timer or retention/deletion policy is introduced.
