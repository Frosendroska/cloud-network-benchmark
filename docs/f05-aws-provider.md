# F05 AWS provider implementation

F05 adds an AWS-specific provider adapter with an isolated regional SSM Automation safety root and a separately applied two-VM topology root. `AwsProviderDriver.register_expiry` requires the active reservation and dated cost identity, registers and reads back a running absolute-time sleep in every involved region, and only then permits pair apply. Its 360-second trigger lead comprises a 300-second discovery/stop window and 60 seconds of planned margin. The Automation script re-queries for the entire bounded horizon using both run and deployment tags, records stop requests separately from observed states, and never deletes resources. A successful stop is compute expiry evidence, not cleanup completion. IAM propagation can be eventual: the role trust and scoped policy are created before start, registration requires a successful readback, and an uncertain start keeps that region's safety resources while blocking pair launch; there is no unbounded propagation wait or automatic retry that could duplicate an execution.

The public runtime entry points are `AwsProviderDriver.register_expiry`, `provision`, and `cleanup`, with settings supplied through `AwsRuntimeSettings`. The pair root selects two On-Demand Ubuntu 24.04 amd64 `m7i.xlarge` VMs, 32 GiB gp3 root volumes, fixed scenario-specific Frankfurt/London subnets and private benchmark ingress. The adapter revalidates the account, instance ownership tags, image owner/architecture, instance type, physical zone ID, placement group, addresses, root volume and console-authenticated ED25519 host key before creating strict attempt-local `known_hosts`. State, tfvars, command records and host trust files are private and isolated by run/deployment. A failed or unreadable attempt journal, residual resources, or uncertain inventory blocks another AWS attempt for that run. Cleanup attempts Terraform destroy, independently inventories tagged resources in every involved region, waits for compute absence before cancelling expiry, then destroys and API-verifies the regional document and role.

The scenario admission evidence and network values are supplied by the caller and must remain sourced; this adapter does not invent an S4 review or imply that a throughput ceiling is observed. The dated public SSM pricing fixture assumes no free tier. Its two-step allowance includes the 300-second discovery horizon plus a 30-second response allowance within a 330-second Automation action timeout: $0.0139 per region (2 × $0.002 + 330 × $0.00003) and $0.0278 for two regions. The trigger remains 360 seconds before the unchanged reservation cap end, leaving 30 seconds between the configured action timeout and trigger; that is planned margin, not a provider stop or billing guarantee. Metadata distinguishes the 300-second discovery horizon, 330-second action timeout, planned margin, and observed step/stop evidence. The cost fixture hash is part of the admitted source identity, so an insufficient or changed reservation input remains a launch refusal. Response fixtures preserve the SSM start execution ID, confirmed InProgress sleep step and absolute timestamp, and authenticated host console boot ID and ED25519 fingerprint. Failure fixtures name incomplete or inaccessible API states; none are AWS observations. Expiry automation has startup, stop latency, and late-creation limits; later paid acceptance must verify the registered safety role and real resource behavior.

## Convergence repairs and offline checks

The convergence repair closes the AWS Automation trust scope with the execution ARN while retaining account, region and tag boundaries; gives each regional role and SSM document a collision-resistant attempt digest; reuses the shared Frankfurt subnet for same-zone and placement runs; and tags root volumes and implicit ENIs. Cleanup now retains instance, boot-volume and network-interface IDs before output normalization, treats missing or malformed inventory collections as unknown, and keeps the primary provisioning failure while recording cleanup exceptions and launch blockers. SSM readback uses its actual scalar `StepExecutions.Inputs` values, binds execution IDs, and bounds Pending confirmation to one registration deadline. The inline discovery checks the 300-second horizon throughout pagination and work inside a 330-second action timeout. Console verification consumes the AWS CLI-decoded `Output`, compares its update timestamp to the observed launch time, rejects replayed boot markers, and records redacted account/region/instance/boot/fingerprint evidence. Cleanup journals terminal regional Automation status and returned action outputs, then clears launch authorization only after safety resources are removed.

Phase 8 repairs additionally decode JSON-literal SSM input strings, reject truncated or ambiguous step histories, and scope the registration deadline away from terminal cleanup while applying a separate bounded cleanup budget. Terminal evidence is checked against the recorded execution ID, document/version, region, exact parameters, expiry timestamp and complete step list; the complete step observations and their outputs are retained. Failed or timed-out executions produce failed expiry evidence rather than being reported as a successful trigger. Known-ID absence accepts only the exact EC2 NotFound code for the recorded resource and region after confirming the configured AWS account. The dated cost fixture now covers two steps and 330 action seconds: `$0.0139` per region and `$0.0278` for two regions, with the 300-second discovery horizon and 30-second return allowance identified separately.

Phase 9 checks the reserved amount against the scoped AWS expiry allowance (`$0.0139` per unique region) before any AWS command and requires the provider settings to carry a sourced complete-workflow handoff that matches the cost source, fixture ID/hash, regions and included amount. This check establishes only that the caller's reservation and handoff cover this expiry allowance; it does not prove that the complete workflow budget is sufficient, which remains the admission/F11 owner's responsibility. Terminal Automation verification follows the document's sleep-then-`aws:executeScript` sequence: top-level Success requires a successful stop step and a single run/deployment-bound `OutputPayload`; a stop step still InProgress after successful sleep is recognized as active and receives bounded cancellation/readback. Per-step payload evidence preserves observed instance states, stop requests and errors. Regional aggregation reports mixed Success+Cancelled as triggered, reports Failed/TimedOut as failed, and reports all-Cancelled as cancelled. These response fixtures follow the AWS [Automation status reference](https://docs.aws.amazon.com/en_en/systems-manager/latest/userguide/automation-statuses.html), [GetAutomationExecution API](https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_GetAutomationExecution.html), and [aws:executeScript reference](https://docs.aws.amazon.com/systems-manager/latest/userguide/automation-action-executeScript.html); they remain offline fixtures, not AWS observations.
