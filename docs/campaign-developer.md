# Campaign driver contracts and supervised acceptance

The [operator guide](campaign-runner.md) is the deployment entry point. This document describes evidence and recovery contracts. Offline implementation does not authorize a paid attempt, establish advisor approval or prove unattended operation.

## One settings file, real evidence

Copy `plans/operator-settings.example.yaml` outside Git. The four small stage plans select existing registered configurations and reference this file. Absolute paths must exist where required and must not traverse symlinks. Private state and exportable results must be separate, non-overlapping roots. Keep dated source documents under a persistent private evidence directory; retain their exact bytes for all stages and later audit.

The settings deliberately contain nulls and false confirmations. Complete them from actual observations:

| Input | Required evidence |
| --- | --- |
| Provider settings | Intended AWS account, Azure subscription/tenant and GCP project; concrete supported Ubuntu images; public/private SSH key paths; controller public IPv4 `/32`; verified VM interface names. Identity checks are bounded read-only commands, not IAM or placement certification. |
| `credential_refresh` | Actual service-identity renewal test, source path and UTC validity through the final slot plus cleanup. Prove both CLI and Terraform access after the original token lifetime. Never place token/key contents here. |
| `approvals` | Explicit `confirmed: true` only after a person reviews the named source. `f10_offline`, `paid_authorization` and `quota_review` apply to every stage. Quota evidence covers 4 benchmark VMs / 16 vCPUs per cloud for overlapping P0/P1, relevant regional capacity, placement and expiry permissions. The controller is separate. |
| Later stage gates | Calibration additionally needs actual paid acceptance and `calibration_authorized`; DAY needs acceptance, `common_n`, `diagnostic_day_authorized`, `size_export_review`; WEEK needs acceptance, `common_n` and `study_window`. These records preserve the source and its hash. They do not manufacture an approval. |
| `pricing` | Dated real quotes/register and expiry-support evidence, all seven complete-workflow USD components for each provider/mode, and reviewed funding. Amounts cover setup, measurement, copy, cleanup, disks, addresses, traffic/export, tax, uncertainty and expiry support. No test fixtures or assumed free tiers. |
| Stage `allowance` | Reviewed conservative initial acceptance bounds; measured registration/provision/readiness/stabilization/measurement/shutdown/retrieval/cleanup seconds and provider expiry leads for scheduled stages. Label initial estimates explicitly; no extra timing pilot is implied. `measurement_seconds` includes shutdown allowance; stabilization remains 60 seconds. Complete workflow plus the largest expiry lead must fit 1,200 seconds for acceptance/short runs, 1,800 for calibration and 87,600 for DAY. |
| Common N | The saved local `lifecycle recommend-common-n --format json` output from three actual valid calibration results; explicit source-backed review. The runner validates and freezes it without selecting N. |
| DAY size/export | Positive measured log bytes and seconds, conservative projected total native bytes, actual verified export bytes and checksum confirmation. Projection must cover measured growth over 86,400 seconds and account for every provider/VM/output. Check guest free space within the configured 32 GiB boot disks and the registered export allowance separately; aggregate controller free space alone cannot prove either. Controller reserve must cover native data plus export staging. |
| UTC schedule | Future calibration/DAY start, or WEEK first day and four distinct reviewed `HH:MM:SS` UTC windows. DAY coverage analysis and human selection happen locally. No inferred or automatic repeat windows. |

All-stage pricing is frozen once into `cost-inputs.json`, with provider/config envelope templates that bind each actual initialized run ID. One ledger, budget scope, source and persisted controller session serve both concurrent calls. Funding remains within the $250 working limit and protects $50 of the $300 cap. The driver does not spend a replacement allocation automatically. A changed price/support source blocks new preparation and requires engineering maintenance with the original sources, ledger and private recovery preserved. The campaign CLI has no price-source replacement command. Do not delete, reset or overwrite those files to bypass the block.

Scalar price components are whole-workflow USD totals for one pair/provider. Advanced component mappings accept `amount_usd`, positive `quantity`, `unit`, `inclusion_rule` and `funding_bucket`; the amount already represents that component total. AWS expiry uses the reviewed step/second rates with the existing two-step / 330-second bound, rounded up. Azure uses its reviewed job-minute bound. GCP zero support cost requires an actual documented rationale. These generated provider support documents never substitute for source quotes.

For `paid_acceptance.source`, use the original private acceptance `prepared-stage.json`. After actual supervision, fill `stage_inputs.acceptance.failure_checks` in the same settings file. Each action source must identify that registered attempt's actual parent campaign ID. The driver generates internal scope/failure reviews and hashes; the operator does not construct internal JSON. Admission replays valid V-S1/V-S3 native evidence and verifies original runtime account/project/image scope. Changing that scope invalidates prior acceptance. Distinct failure attempts require actual server-failure, physical controller-loss, independent expiry and full-cleanup source records. Ordinary lifecycle success cannot satisfy these checks.

## Journal and execution boundaries

Preparation persists all manifest identities, frozen config/schedule/runtime/source hashes, per-entry private directories and planned UTC slots before the service is started. Generated executable configs live in ignored `configs/{tests,experiments}/campaign-generated/`; retain them with original private recovery state. Schedule-aware initialization preserves the schedule row/hash. Unique deployment/placement/work/state/log paths and isolated Terraform data directories prevent simultaneous calls sharing provider state.

One nonblocking OS file lock protects the driver. Entry states are `scheduled`, `starting`, `running`, `complete`, `failed` and `missed`. Setup begins only at the measured lead; late wakeups leave the slot missed. WEEK uses two independent all-cloud lifecycle calls at each of 28 slots. A failed measurement with proved cleanup preserves its evidence and allows later slots; cleanup liabilities or uncertain launch stop new work. Acceptance baseline failures stop the remaining stage; registered failure attempts require an explicit supervision continuation. A confirmed continuation may also run bounded cleanup-only reconciliation for an earlier liability using its original private journal/session; it never retries the measurement. Unattempted failure checks remain pending until that liability is proved closed.

`lifecycle run --execution-scope paid_request` remains the execution boundary with unchanged admission, reservation, expiry and cleanup guards. Supervisor restart reconciles original manifests/private recovery; it never starts the measurement again. A clean terminal result exits the service normally, including recorded failures, avoiding terminal-failure restart loops. Unexpected interruption permits service restart and reconciliation. `check` and start without `--execute` do not initialize paid runs, reserve budget or provision resources. Checking invokes only local validation and bounded identity reads, including an ADC usability probe whose output/errors are discarded.

Controller logs rotate at 5 MiB with three backups; raw/native/provider evidence never rotates. Atomic journal replacements flush both file and directory. Optional hook delivery records an intent before invocation: this prevents duplicate sends after restart, but a crash in that interval can lose delivery. Inspect status rather than treating the hook as a reliable alerting service. An optional backup destination receives verified closed bundles; verify the mount is physically separate before calling it off-machine protection.

## Supervised registered failure checks

These instructions are a preparation procedure for a separately authorized paid acceptance session. They do not record a pass. Use exactly the registered V-A-FAIL, V-Z-FAIL and V-G-FAIL attempts, one provider at a time. V-S1 and V-S3 must first have real native validation, placement readback and closed cleanup. Preserve the registered caps; do not extend deadlines or add an unregistered pilot to make a check pass.

1. From a second machine, prepare authenticated runner hypervisor/management-console access capable of **abrupt power-off** and later power-on. Record the original stage, entry, parent campaign ID, saved session and recovery paths. Keep a separate protected copy of necessary cleanup references outside the runner before the cut; never put private journals in public results. Prepare independent read-only provider observation with a trusted UTC clock.
2. Before `campaign continue`, identify how to read actual deployment IDs, VM B addresses, authenticated SSH users/key paths and known-hosts paths from original private provider/access evidence. Have the second-machine observation/injection procedure ready. Do not guess resources from naming prefixes or weaken host-key checks.
3. Run `campaign continue --stage-id ACTUAL_STAGE_ID --entry-id V-A-FAIL --confirm-supervision` on the runner (substitute the other registered ID for Azure/GCP). Watch real provisioning, expiry registration and measurement readiness. Capture original expiry deadlines and provider resource identifiers from durable native evidence. If the required timing or evidence is unavailable, stop and retain the failed acceptance record.
4. While the registered measurement is active, inject the approved benchmark server failure on VM B. For the current bootstrap listener, the exact unit is `cnb-ACTUAL_DEPLOYMENT_ID-iperf3.service`. An authenticated command is:

   ```sh
   ssh -i ACTUAL_KEY -o UserKnownHostsFile=ACTUAL_KNOWN_HOSTS -o StrictHostKeyChecking=yes ACTUAL_USER@ACTUAL_VM_B 'sudo systemctl stop cnb-ACTUAL_DEPLOYMENT_ID-iperf3.service'
   ```

   Verify the actual unit/deployment identity first. Save command time, server state and available failure evidence. Then use the prepared hypervisor control to cut power to the **runner**, before its normal controller cleanup completes. A guest shutdown, `systemctl stop`, SIGTERM or closing SSH exercises a different path and cannot establish physical controller loss. Record the abrupt-loss timing relative to the server fault. If this attempt cannot prove both required conditions, mark it inconclusive; do not silently authorize a second paid attempt.
5. Leave the runner off through the original provider expiry deadline. From the second machine, save actual readback showing AWS/GCP compute stopped or Azure compute deallocated under the pre-registered mechanism. Preserve its identities, timestamps and logs. Compute expiry alone leaves disks, addresses or support resources billable and is not full deletion proof.
6. Restart the runner. Confirm the same private journal/session is reconciled, with no new measurement. Inspect cleanup results; if required use the original `lifecycle cleanup --recovery ... --controller-session ... --format json`. Verify absence of every experiment VM, disk, address, placement and support resource from original inventory. Record any residual liabilities and resolve them before another attempt/stage. Never target the runner or shared unrelated resources.
7. Retain all available local native files, partial export and failure logs. Review actual server failure, abrupt controller loss, independent expiry and complete deletion as separate facts. In the operator file, confirm each fact only after its source record exists and contains the actual attempt ID. Inconclusive timing, missing evidence or open cleanup blocks acceptance; implementation cannot turn it into a pass.

A physical controller loss before post-measurement retrieval can strand native files on stopped guest disks; cleanup can remove those files. Automatic VM restart/disk rescue is outside this driver. Preserve available controller copies and report missing native evidence explicitly. If recovering guest-only files would require another paid action or extending the protocol, obtain a separate decision before that action; do not claim successful collection. Physical loss of the controller disk also requires its independent private recovery copy. Disconnecting SSH normally is a separate non-destructive service check and should leave the same driver PID/session and stage journal active.

## Portable exports and local replay

Each cleanup-closed entry seals available files and verifies copied checksums. Partial failures remain exported, but incomplete/invalid validation descriptors are not advertised as analyzable. The aggregate `export/selection.json` references closed bundles without copying all raw bytes a second time. Exported manifests, saved validation inputs/results and relocated DTOs retain original checksums/provenance while rebasing locations. Do not edit the sealed originals. Hash/copy operations stream files. Credentials, SSH keys, Terraform state and original recovery journals remain private.

On the laptop, copy the entire stage result tree and use the existing `analyze` command. It revalidates native evidence; the runner performs only necessary validation and collection. Keep the runner originals until local checksums/replay succeed. A local-only closed bundle is still vulnerable to controller-disk loss. Optional backup protects closed exports, not in-progress guest files or private recovery state.

Acceptance records sampled controller-process RSS, the lowest sampled free space and the observed consumption delta on the shared results filesystem. Other writes and the concurrent call can contribute to that disk delta; do not sum it as independent per-run storage. Controller subprocess peaks and test-fixture disk measurements are scoped engineering evidence; they do not measure all provider processes, the entire VM or the future DAY volume. See [validation evidence](validation/campaign-driver.md) for actual commands, counts and remaining Linux/cloud checks.
