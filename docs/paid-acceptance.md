# Controlled paid acceptance handoff

F10 ends at credential-free offline proof. This document describes a future stage; it grants no launch authorization and records no completed cloud validation. Real provider behavior, Linux process semantics, instrumented binaries, current prices, quotas, calibrated N and study windows remain unproved or pending.

## Entry checks and registration

Before any authorized acceptance, refresh dated provider prices and quotas from the linked run register, verify available quotas, and reserve the complete workflow cost and lifetime within the $300 cap while protecting the $50 buffer. Retain active reservations for unfinished primary work. Record the source register revision, input date, currency/tax/uncertainty, provider limits, reservation IDs and run/config hashes. Register and verify independent provider-side compute expiry for every provider before VM creation; guest shutdown, AWS/GCP stop and Azure deallocation do not prove full cleanup. Expiry registration failure blocks creation. Keep AWS, Azure and GCP states/results isolated and retain evidence for all billable resources.

Use strict SSH host identity, source-built guest tools and receiver-side iperf3 streaming. Record source/build hashes, patch and capability evidence, exact commands, process start/stop times, measured windows, schedules, resource IDs and Git provenance. Copy native Sockperf CSV and iperf3 JSON/JSONL after measurement, close and verify bytes/checksums before cleanup. Preserve failures, incomplete transfers and partial native evidence. Cleanup must delete and verify VMs, disks, addresses and all other billable resources; unresolved cleanup blocks later launches.

## Registered acceptance sequence

Run the registered V-S1 all-cloud acceptance with ten measured seconds per phase and N=4 before calibration. Then run V-A-FAIL, V-Z-FAIL and V-G-FAIL server-failure/controller-loss cases to prove failure preservation, provider expiry fallback, retrieval and full cleanup. A physical controller-loss test must show provider-side expiry and complete deletion. Acceptance is not research data. After these checks, perform the separately registered V-S3 workflow. V-S2 and V-S4 remain separately gated; admit neither without the required P0/P1 analysis and budget review.

Native Linux acceptance must execute the two Darwin `/proc` gaps from [F10 evidence](validation/f10-offline-gate.md) and verify process/session identity behavior. On the authorized Linux guest, execute the pinned instrumented Sockperf and iperf3 builds and show the exact source, patches, build identity, capabilities, receiver stream, restart/chunk evidence and resulting native files. F10's fakes and source-patch tests do not establish these behaviors.

## Calibration, storage and diagnostic day

Run CAL-S1 on one separate retained S1 pair per cloud: 1/2/4/8 streams, three 60-second loaded trials for each count, ten-second pauses, in the fixed orders 1,4,2,8; 8,2,4,1; and 2,8,1,4. Select the smallest common N in {2,4,8} reaching at least 95% of each cloud's best tested median; otherwise use N=8 and report that no common plateau was found. Freeze the resulting common N and resolved configuration before research. Calibration outputs are workload selection evidence, not research results.

Measure actual diagnostic log growth and establish disk/export feasibility against the 32-GiB boot disks and 20-GiB per-cloud export allowance before admitting DAY. Use separate retained pairs for each cloud. DAY consists of one continuous 86,400-second aggregate TCP interval, one warm-up, no scheduled TCP restart, local probe chunks no longer than 300 seconds, and one-second local diagnostics. Preserve receiver evidence and incomplete chunks. Analyze the full TCP duration and require at least 99% RTT time coverage before selecting exact UTC morning/afternoon/evening/night study windows. Review incomplete evidence and remaining budget; no DAY retry is automatic.

Exact N, UTC windows, refreshed prices, quotas and realized costs stay pending until their source evidence is available and the required authorization is given. F10 itself performs none of these steps.
