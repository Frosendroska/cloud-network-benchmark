# WEEK observer generation repair

The WEEK stage factory omitted `week` from the two observer stage gates in
`campaign_inputs.prepare_stage`. A generated WEEK therefore had neither runtime
observer configuration nor the prepared-stage campaign/receipt/binding paths.
The fix adds WEEK to those two existing gates. It does not change scheduling,
provider implementations, measurement protocols, financial admission or retries.

This document preserves the original isolated-branch evidence. That change is
now included in the combined integration candidate at `f13ff35`; the integrated
Linux qualification is recorded in [the WEEK integration report](week-integration.md).

The reproduced baseline is `bed9b98893540e52a0433a3213f20e75b3dd0d1d`, tree
`15eaae842d9db6d0df3c142d1c2965d31d883a0c`, identified by the durable
`WEEK_DETACHED_READINESS.md` copy on Halle. Keep this repair separate from existing
paid cards and frozen inputs. Generated runtimes now have different hashes and
must be generated/reviewed through the ordinary preparation path for any future
authorized integration; do not hand-edit an existing prepared stage.

## Regression and native qualification

`tests/integration/test_week_observer_chain.py` generates the complete 56-entry,
168-child WEEK through the production factory and validates every observer
configuration and persisted runtime hash. An active first S1/S3 pair exercises:

1. Production journal/prepared-stage persistence and `build_runtime`.
2. All six real provider remote-stage adapters, including their preparation,
   stabilization and measurement callback forwarding.
3. `LocalMeasurementProcesses` and `GuestObserverProgress` capturing real Linux
   PID, boot ID and start ticks from owned, bounded local fixture processes.
4. The actual lifecycle publisher, complete-active-set aggregation, create-only
   launch receipt, bindings, SHA-256 pins and prepared-stage update.
5. The real supervisor consumer and unchanged guest probe program, executing
   against Linux `/proc` through a local guest-transport fixture.

Positive evidence is generated by these production paths. No observer config,
launch receipt or binding JSON is authored by the test. Negative tests corrupt
copies of the emitted artifacts to reach hash, identity and duplicate guards.

The 13 cases cover all 56 factory bindings; the six-participant publisher and
supervisor chain; missing bindings, receipt and progress; stale diagnostics;
process-identity, binding-hash, run-ID and receipt mismatches; duplicate binding
and prepared entries; and rejection of previous-pair bindings for a new active
pair. Duplicate publication is idempotent and does not replace the existing
immutable receipt. Publication preserves the stage digest and every runtime
hash, so the driver can reread the same journal without a new attempt.

Financial admission and provider workflow creation are explicit test boundaries.
The remote adapter receives an in-memory timing fixture with the original
factory cap; no operational reservation is created. F02/F04 and F03 guest
transport are simulated; local fixtures do not run benchmarks or contact clouds.
The measurement outcome remains an explicit offline fixture failure, rather
than claiming a successful measurement. No provider or credential preflight is
run. Native proof uses existing Halle Python 3.12.3 and `unshare -Urn env -i` to
disable networking and remove inherited credentials/environment variables.

Run the chain on Linux:

```sh
unshare -Urn env -i PATH=/usr/bin:/bin PYTHONPATH=src:. \
  /u/halle/brek/home_at/cnb/venv/bin/python -m pytest -q \
  tests/integration/test_week_observer_chain.py
```

Adjacent qualification includes observer publication/consumption, guest and runtime
contracts, campaign service/driver behavior, and production WEEK generation with
28 paired slots, unique IDs/namespaces, immutable schedules, original caps and
unchanged financial denial. The final external integration handoff records the
exact tested commit/tree, commands, JUnit counts and hashes. Initial fixture
failures remain in the evidence directory; they are not counted as passes.

## Integration boundary

The repair is integrated with the published-main history and the reviewed
paired-failure continuation change in the isolated candidate. It cannot
retroactively supply bindings to a previously generated WEEK. Future stages must
be generated and reviewed through the ordinary preparation path; existing
prepared stages and cards were not changed.

This qualifies the offline observer chain on native Linux. It does not establish
cloud acceptance, real guest/SSH connectivity, credential renewal, notification
delivery, eight-day endurance, host-reboot persistence, resource absence or WEEK
launch authority. The other readiness gates remain separate.
